# Development Plan — Marketplace Sides (custom import, gallery, gamification, community PR path)

**Local repo**: `/Users/nicolas/perso/sidequest`
**Status**: implemented 2026-08-27 (all 9 sprints below, see section 5) — folded into roadmap section 6 of [`plan-mvp-sidequest.md`](plan-mvp-sidequest.md) as the "V1+" entry.

## 1. Vision

The repo already presents SideQuest as a marketplace (README, roadmap), but today only one side ships (**SideGym** / `sport-basic.json`), loaded through a single hardcoded file lookup (`loadSide(sideId)`, `packages/core/src/sides.ts`). The mascot is a global setting fully disconnected from the active side, and the dashboard's side import/export only handles `{name, exercises}` — no mascot, no notion of provenance (official vs. imported vs. custom).

This plan makes three things possible: users **import their own side (exercises + their own mascot) locally**, a real **sides gallery** in the dashboard instead of a plain "Plans" tab, and a documented **community contribution path via PR** — without building the V1.5/V2 infrastructure (dynamic registry, install CLI, paid backend), which stays out of scope and is already tracked in the roadmap.

`Plan` (SQLite, dashboard CRUD) and `Side` (bundled JSON) are today two near-identical, unrelated types — unifying them is the prerequisite that unlocks everything else (a side carrying its own mascot, discovery of more than one bundled side, etc.).

## 2. Locked-in decisions

- **Custom side import format**: a single JSON file, mascot image embedded as base64 — reuses the existing side-import dialog as-is, no zip/folder handling.
- **Sides gallery** in the dashboard is in scope, not just an extension of plan import/export — it's what makes the app read as a marketplace rather than a single "create your training plan" screen.
- **Two additional side ideas** added to the catalog vision: **SideCat** ("look after your cat") and **SideTama** (tamagotchi-like growth). Both are modeled as ordinary `Exercise`-based sides (a popup is a short care action: "feed your cat", "pet it", "let it sleep") — no new side "type" or state-machine engine, to avoid over-building a simulation for what is really "show a progression".
- **Cross-side XP bar** for gamification, additive on top of the existing per-session history (no change to `sessions`/streak logic).
- **Official SideQuest logo** (`docs/branding/SideQuest-logo.png`, transparent PNG, pixel-art explorer mascot, tagline "CODE. QUEST. GROW.") integrated at the top of the README. Its palette (cyan/cream/dark) becomes the app's base brand palette, layered on top of — not replacing — the 4 existing `visualTheme` skins (see [`plan-theme-global.md`](plan-theme-global.md)).
- **Per-side color**: each side carries its own accent color, shown in 3 places — the gallery card badge/border, the XP bar fill, and the overlay's accent color while that side's exercise is showing.

## 3. Technical architecture

### 3.1 Data model unification (`Side` / `Plan`)

Extend `Side` rather than keep two parallel types; `Plan` becomes a type alias of `Side`.

- **`packages/core/src/sides.ts`**: add `SideSource = "bundled" | "imported" | "custom"`, `SideMascot { id, label, imagePath }` (absolute file path, base64 is never stored as-is), extend `Side` with `source: SideSource`, `mascot?: SideMascot`, `color?: string` (hex — added here directly to avoid a second migration later, used in 3.5). `loadSide()` tags its result `source: "bundled"`. New `listBundledSides(): Side[]` scans `src/exercises/*.json` instead of the current single hardcoded lookup — this is what lets several bundled sides (SideGym + future community sides merged via PR, 3.6) be discovered with zero code change.
- **`packages/core/src/storage.ts`**: replace the local `Plan` interface with `export type Plan = Side;`. `sides` table gains `source TEXT NOT NULL DEFAULT 'custom'`, `mascot_id`, `mascot_label`, `mascot_image_path`, `color TEXT` via the same additive-migration pattern already used for `sessions.mascot`/`sessions.mode`. `createSide(name, exercises, opts?: { source?, mascot?, color? })` defaults to `source: "custom"` so existing plans keep working unchanged. `deleteSide` stays as-is in core (no fs access there); mascot file cleanup happens app-side (3.2).

No new dependency (no zod) — kept consistent with the existing hand-rolled validation style.

### 3.2 Custom side import (exercises + own mascot)

Import format — a single JSON file, `mascot` optional:

```json
{
  "name": "SideYoga - Douceur",
  "mascot": { "label": "Yogi", "image": "data:image/png;base64,iVBORw0KGgo..." },
  "exercises": [{ "id": "stretch-1", "label": "Étirement dos", "durationSec": 30, "category": "étirement" }]
}
```

- **`packages/app/src/main/index.js`**: extend `dashboard:import-side` — validate `mascot.image` against `data:image/(png|jpe?g|webp);base64,...`, cap the decoded size (~3 MB), decode with `Buffer.from(..., "base64")`, write to `path.join(app.getPath("userData"), "custom-mascots", `${randomUUID()}.${ext}`)`. The base64 blob is **never** stored in SQLite — only the resulting absolute path, via `storage.createSide(..., { source: "imported", mascot })`. Extend `dashboard:export-side` to re-embed the mascot as base64 for a lossless round-trip (this doubles as the sharing mechanism for 3.6's PR path). Extend `dashboard:delete-side` to best-effort `unlinkSync` a mascot file living under `userData/custom-mascots/`. `showExercise()` exposes `payload.mascotImage` (`file://` + path) so the overlay never needs filesystem access itself.
- **Mascot resolution de-duplication**: `MASCOT_LABELS`/`MASCOT_IMAGES`/`resolveMascotImage` are currently duplicated in `dashboard/renderer.js` and `overlay/renderer.js`. New shared `packages/app/src/shared/mascots.js`, loaded via `<script defer>` in both `index.html` files, single source of truth. `resolveMascotImage(mascotId, theme, overrideImageUrl?)` gains an optional 3rd argument that short-circuits to a resolved custom image when provided.

**Risks**: base64 size cap (new constant, no repo precedent — document inline); context isolation preserved (renderer never gets direct fs access, everything flows through IPC like today); orphaned-file cleanup stays best-effort, no startup GC pass.

**Explicitly out of scope**: zip/folder import, multi-file drag-and-drop, animated mascots (gif/Rive) — png/jpg/webp static only, matching today's bundled mascots.

### 3.3 Sides gallery in the dashboard

Reuses the existing "Plans" tab (`dashboard/renderer.js`, panel in `index.html`) rather than a second screen — the actual gap is multi-side discovery, not the grid UI, which already exists.

- **`main/index.js`**: `dashboard:get-sides` returns `{ bundledSides: listBundledSides(), customSides: storage.getSides() }` instead of the singular `defaultPlan: loadSide("sport-basic")`. `dashboard:export-side`'s `sport-basic` special case generalizes to a lookup in `listBundledSides()` by id.
- **`dashboard/renderer.js`**: `allSides()` concatenates `bundledSides` + `customSides`. `renderSidesGrid()` adds a mascot thumbnail per card (via the shared `resolveMascotImage`), a provenance badge ("Official" / "Imported" / none for "Custom"), and generalizes the "can't delete" rule from `id === DEFAULT_SIDE_ID` to `source === "bundled"`.
- **`dashboard/index.html` + i18n files**: cosmetic rename "Plans" → "Sides" / "Sides gallery" (open for naming bikeshedding), import button label.

**Risk to verify**: `packages/app/package.json`'s electron-builder `files` doesn't explicitly list `packages/core/dist/exercises/*.json` — it already works today for the single `sport-basic.json` via workspace dependency resolution, but this is the first time multi-side discovery is exercised in a packaged build → run `pnpm run build` + a packaged-app smoke test once `listBundledSides()` ships.

**Explicitly out of scope**: search/filter, ratings, remote/downloadable sides.

### 3.4 XP bar (gamification) + SideCat / SideTama sides

- **`packages/core/src/storage.ts`**: new `side_progress (side_id TEXT PRIMARY KEY, xp INTEGER NOT NULL DEFAULT 0, level INTEGER NOT NULL DEFAULT 1)` table, created alongside `sides`/`sessions` in `migrate()`. `addXp(sideId, amount)` increments `xp` and recomputes `level` with a deliberately simple v1 formula: `level = Math.floor(xp / 100) + 1` (no per-side curve yet). `getSideProgress(sideId)` reads, defaulting to `{ xp: 0, level: 1 }`.
- **`main/index.js`**: in `recordAndHide(status)`, right after `storage.recordSession(...)`, call `storage.addXp(currentPlan.id, XP_PER_EXERCISE)` (flat constant, e.g. `10`) when `status === "done"`. New `dashboard:get-side-progress` handler feeds the gallery's bar.
- **`packages/core/src/sides.ts`**: `SideMascot` gains an optional `stages?: { minLevel: number; imagePath: string }[]` — generic, not pet-specific, but what lets SideCat/SideTama visually grow with level (kitten → cat → majestic cat; egg → baby → adult), on the same principle as the existing `MASCOT_LIGHT_VARIANTS` mechanism but keyed by level instead of theme. Sides without `stages` (SideGym, SideYoga...) just show the bar without a mascot change.
- **`dashboard/renderer.js`**: gallery card gains a progress bar (`xp % 100` width, "Level N" label) below the mascot thumbnail. Shared `resolveMascotImage` resolves the highest `stage` whose `minLevel <= level` when `mascot.stages` is set — used by both the gallery and the overlay.
- **Two example sides** (illustrative — either shipped as JSON under `packages/core/src/exercises/` or kept as examples in 3.6's doc):
  - **SideCat** — care actions ("Feed your cat (10s)", "Scratch its ears", "Change the litter box"); hook line: **Your cat exists even when you're coding.** A pet, a bowl, 30 seconds. It grows with your streak, not your guilt.
  - **SideTama** — care actions ("Feed it", "Play with it", "Let it sleep"); hook line: **Your tamagotchi doesn't judge your commits, it grows with them.** 30 seconds, one more level.

**Explicitly out of scope (v1)**: no decay/hunger over time (no real tamagotchi that "dies"), no per-side/per-exercise XP formula, no level reset/prestige, no server/leaderboard for XP (see V2 in `plan-mvp-sidequest.md`) — the bar stays a local, cosmetic indicator.

### 3.6 Community contribution via PR (docs only)

New doc, `docs/plan-community-sides.md`, linked from the V1.5 roadmap row:

1. **Mechanic possible today with zero extra code** (thanks to 3.1/3.3): a contributor adds a side JSON (`packages/core/src/exercises/`) + a mascot image (`packages/app/assets/mascots/`, optionally several `stages`) via PR. `listBundledSides()` picks it up automatically — no registry file to edit.
2. **Limitation to state explicitly**: a merged side only reaches users on the **next tagged release** (no dynamic registry = no hot install) — unlike 3.2's local JSON import, which works **instantly, offline**. This is the key thing to communicate to a contributor.
3. **Relationship to the existing roadmap**, without contradicting it: this PR path is a lightweight, manual (regular human code review) precursor to V1.5 (`sidequest install <side>`, dynamic registry) and V3 (paid, formally-reviewed third-party marketplace) already described in `plan-mvp-sidequest.md`.
4. **Constraints carried over**: sides stay purely declarative JSON (same security rationale as `sides.ts`'s existing comment); no CI schema-validation bot, no art-licensing requirement for now — left to human review, deliberately not over-engineered.

### 3.7 Bundled side translation (fr/en) — done, 2026-08-27

The dashboard has been bilingual (fr/en) since before this plan, but side content itself — `Side.name`, `Exercise.label`/`.category` — was always plain French text baked into the JSON, untranslated regardless of the UI language. Fixed for bundled sides only (SideGym, SideCat, SideTama, and any future one added via 3.6's PR path):

- **`packages/core/src/sides.ts`**: `Side`/`Exercise` gain optional `nameEn`/`labelEn`/`categoryEn` fields — French stays the reference (`name`/`label`/`category`, unchanged), English is an override only present on bundled sides. New `translateSide(side, language)`: returns the side as-is for `"fr"`, or with every `*En` field substituted in for `"en"` (falling back to the French field if a specific translation is missing) — same default-fr/override-en pattern already used by every `t()` dictionary in the app (`dashboard/i18n.js`, `main/i18n.js`). A no-op on custom/imported/generated sides, which never have `*En` fields (user content, already in whatever language the user wrote it in) — safe to call unconditionally without checking `source` first.
- All three bundled side JSON files got full English translations (name + every exercise's label/category).
- **`packages/app/src/main/index.js`**: `loadActiveProgram()` now translates before returning — the single choke point already shared by `showExercise()` (overlay) and `dashboard:get-exercises` (history table), so both picked up translation for free from one change. `dashboard:get-sides` translates `bundledSides` (not `customSides`) before sending to the renderer. `dashboard:export-side` translates too, so an exported file matches what's currently on screen.
- **`packages/app/src/dashboard/renderer.js`**: the language-change branch in `applySettingsToUI()` now calls `refreshSides()` (re-fetch over IPC) instead of `renderSidesGrid()` (re-render from the already-cached, already-stale-language response) — translation happens server-side in main, so the renderer needs a fresh fetch to see it.

Verified live: switching the dashboard's language bubble from fr→en retranslates the gallery card names (`"SideCat - S'occuper de son chat"` → `"SideCat - Look After Your Cat"`), the read-only exercise list in a bundled side's editor, and — checked via `dashboard:get-exercises` directly, since it's the exact function the overlay's `showExercise()` also calls — all 12 of SideGym's exercise labels (`"Gainage"` → `"Plank"`, `"10 pompes"` → `"10 push-ups"`, etc.).

**Left as a known, narrow gap**: if a bundled side is open in the (read-only) side editor at the moment the language changes, its exercise list won't retranslate until closed and reopened — `editingSide` is a local snapshot, not re-fetched on language change, and re-fetching it live wasn't judged worth the complexity for a read-only view of a rare timing coincidence.

### 3.8 Side-level mascot picker — done, 2026-08-27

Before this, the only way to give a side its own mascot was 3.2's import flow — hand-craft a JSON file with a base64-embedded image. Now the side editor (custom/imported/generated sides — bundled sides stay read-only, same treatment as their name/exercise fields) has a "Mascotte" card: every bundled mascot as a selectable tile, plus a **"+ Add"** tile to upload your own image file directly, no JSON required.

- **`packages/core/src/storage.ts`**: `updateSide()` gains a third optional field, `mascot?: SideMascot | null` — `null` explicitly clears it (falls back to the global mascot), an absent key leaves it untouched, a `SideMascot` replaces it. Needed a `"mascot" in partial"` check rather than relying on the existing spread-based merge, since `undefined` (not provided) and `null` (clear it) have to mean different things here.
- **`packages/app/src/main/index.js`**: three new IPC handlers. `dashboard:set-side-mascot-bundled` resolves one of the app's own bundled mascot PNGs to an absolute path (`ASSETS_DIR/mascots/<id>.png`) and assigns it directly — no file copy needed, it's already shipped with the app. `dashboard:set-side-mascot-custom` opens a native file dialog (png/jpg/webp, same 3 MB cap as import) and copies the chosen file into `userData/custom-mascots/` via a new `storeMascotFile()` — structurally the same as 3.2's `decodeMascotImage()`, just reading a real file instead of decoding base64 (no base64 round-trip needed when a native file path is already in hand). `dashboard:clear-side-mascot` resets to `null`. All three best-effort clean up the *previous* custom mascot file via a new shared `cleanupCustomMascotFile()` helper (`dashboard:delete-side`'s inline cleanup was refactored to reuse it too).
- **UI** (`dashboard/renderer.js` + `index.html`): the picker shows **all** bundled mascots, not theme-filtered (a side's identity shouldn't depend on which dashboard skin happens to be active). Clicking the already-active tile clears it (toggle, same convention as the gallery's Activate/Deactivate button) rather than needing a separate "clear" affordance. A side's existing custom mascot (from import or from this picker) shows as its own active tile, also clickable to clear.
- **The "+" tile is deliberately named generically** ("+ Add", not "+ Upload"/"+ Import") to leave room for a second option later — generating a mascot image via AI, alongside the already-shipped [plan-llm-side-generation.md](plan-llm-side-generation.md) side-*content* generation — without a rename. Not built yet; today "+" only opens the file dialog.
- **The Settings page's own global mascot picker was removed** (`#mascot-options`, `renderMascotOptions()`) — mascot choice is now a *side* property, not a separate global preference, so keeping both would have been redundant and confusing about which one actually wins. `Settings.activeMascot` itself, its storage, and the `visualTheme`-switch auto-reassignment logic are untouched (still the fallback mascot for a side with none of its own) — only the settings-page widget to hand-pick it directly is gone. Onboarding copy updated to stop mentioning "your mascot" as something to configure there.
- **Upload validation strengthened past extension + byte size**: a new shared `isValidMascotImageBuffer()` (used by both this picker's `storeMascotFile()` and 3.2's `decodeMascotImage()`) now actually decodes the file via Electron's `nativeImage` and checks it isn't empty (`isEmpty()` — catches a file whose extension lies about its real content) *and* caps pixel dimensions at 2048×2048 — generous next to the 72px display size, but stops a well-compressed-but-enormous image from being accepted just because its byte size looks fine.

Verified live: a new side's editor renders all 8 tiles (7 bundled + "+"), picking one shows exactly one active tile and updates the gallery thumbnail, re-clicking it clears back to zero active tiles; the Settings page no longer has a mascot section. Upload validation verified via a temporarily-stubbed `dialog.showOpenDialog` (the real dialog can't be scripted like DOM clicks) driving the actual `dashboard:set-side-mascot-custom` handler end to end: a real 1024×1024 bundled mascot PNG is accepted, and the 2092px-wide SideQuest logo is correctly rejected by the new dimension cap with the expected error message.

## 4. Functional scope

**Included**
- Custom side import (exercises + own mascot, base64 single-file JSON)
- Sides gallery replacing the single "Plans" tab (bundled + imported sides, provenance badges, mascot thumbnails)
- Per-side XP bar + level, with mascot growth stages for sides that define them
- Two new example sides: SideCat, SideTama
- Official logo in the README + base brand palette + per-side color (gallery, XP bar, overlay)
- Community contribution documented as a PR-based path (docs only)
- Bundled side content (name, exercise labels/categories) translated fr/en on language switch
- Side-level mascot picker in the editor — bundled mascots or a locally-uploaded image, no JSON import required

**Excluded (later roadmap, V1.5+)**
- Dynamic side registry / `sidequest install <side>` CLI
- Zip/folder side bundles, drag-and-drop
- XP leaderboard / server-side anything
- Reviewed, paid third-party marketplace (V3)
